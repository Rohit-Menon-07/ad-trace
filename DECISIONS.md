# DECISIONS.md

Deviations from docs/SPEC.md and choices made where it was ambiguous. One line each: decision, then reason. Newest at the bottom.

## Prompt 1: scaffold + frontend shell

1. **Raw file name.** The real file is `data/raw/AD Notice of Proposed Rulemaking (AD NPRM).xlsx` (spaces and parentheses), not the underscored name in SPEC §2. `config.yaml` points at the real name. *Reason: match what is on disk; don't rename source data.*
2. **`RecordCard` and `ExcludedRecord` defined by us.** SPEC §7 uses them but doesn't define them. Fields are in `frontend/src/types/api.ts`. RecordCard holds status, comment period, lineage, models, model-list confidence and retrieval score. ExcludedRecord holds record id, docket, rule id and reason. *Reason: smallest shape that covers the UI spec in §8.*
3. **Extra API types defined:** `LineageEdge`, `RecordDetail` (for `/api/records/{id}`), `MetaResponse`, `CoverageReport`, `EvalResults`. *Reason: SPEC lists these endpoints without response schemas; the backend must match these types or update them.*
4. **No count of dropped claims in `SearchResponse`.** The UI reads `trace[S7].details.claims_dropped` for the "N claims removed" notice. *Reason: no schema change needed, and the code-generated trace already carries it.*
5. **Reason-code copy (title and suggested next action) lives in the frontend** (`components/reasonCodes.ts`). The codes themselves still come only from the backend. *Reason: the refusal card needs a "next action" (§8), but SearchResponse has no field for it; this is UI text, not a decision.*
6. **Source drawer is a fixed right column, not an overlay.** On narrow screens it stacks below the result. *Reason: §8 says "Right: source drawer"; a fixed column is simpler and works with the keyboard (Esc closes it, focus moves to it).*
7. **No router.** Search, Coverage and Evaluation are switched with local state. *Reason: react-router is not in the allowed stack.*
8. **Tailwind v4** (`@tailwindcss/vite`), with class-based dark mode via `@custom-variant`. *Reason: current major version; no PostCSS config needed.*
9. **MOCK labelling.** Mock records use ids `MOCK-R000n`, dockets `MOCK-FAA-…` and citations `MOCK 91 FR …`, with `url: null`. A fuchsia dashed MOCK badge appears in the header, on every mock response, in the source drawer and on Coverage/Evaluation. *Reason: fake data must never look like a real FAA notice.*
10. **Mock evaluation numbers are placeholders.** The Evaluation page shows a "MOCK placeholder numbers. Nothing has been measured" alert. *Reason: the tables must exist now, but no metric has been measured.*
11. **Mock citations are checked at load time.** `mockCite()` throws if a quote is not a substring of its sentence (mirrors H4). *Reason: stops mock quotes drifting from their sources.*
12. **Clarification chip in MOCK mode** fills the model field and serves the "answered" scenario. The real backend will re-run the pipeline. *Reason: mocks can't compute; the behaviour is marked in code.*
13. **`config.yaml` `as_of: null` means "today at request time".** The resolved date is echoed in `SearchResponse.as_of` and in the audit log. *Reason: as_of defaults to today but stays visible and reproducible per request.*
14. **Generated data is git-ignored:** `data/raw/`, `data/processed/*`, `data/index/*`, `logs/*`, and `.env` at any depth (including the existing `data/.env`). *Reason: the source file is not redistributed, derived files are rebuilt by `make ingest`, and logs contain user queries.*
15. **Makefile written, but `make` is not installed on the dev machine (Windows).** Run the commands directly; CLAUDE.md says so. Backend targets in the Makefile are placeholders until the backend exists. *Reason: keep the repo standard without blocking work.*
16. **Applicability verdict for a "series" designation (e.g. "A330-200 series") is UNDETERMINED in the mocks.** It is not treated as APPLICABLE. *Reason: the conservative reading of SPEC S4; the backend will apply the same rule.*

## Prompt 2: typed API contract + mock backend

17. **TS types are generated by our own small JSON Schema → TS converter** (`backend/app/export_types.py`), not by `json-schema-to-typescript`. *Reason: the drift test stays pure pytest with no Node dependency; it only needs to cover the constructs our models produce.*
18. **Requests are generated in validation mode and responses in serialization mode** (`json_schema_serialization_defaults_required`). Request fields with defaults are optional in TS; response fields are always present. *Reason: matches what each side actually sends.*
19. **`SearchResponse.reason_code` is typed `ReasonCode | None` (a closed Literal), not `str | None` as in SPEC §7.** *Reason: stricter. The backend cannot emit a code the UI doesn't know.*
20. **All API models use `extra="forbid"`.** *Reason: unknown request fields get a 422 rather than being silently ignored.*
21. **MOCK search routing (`mocks.choose_scenario`)** uses form fields before keywords:
    - "torque", "part number" or "A350-2000" → refused;
    - a family-only model such as "A330" → needs_clarification;
    - an A320 model, a serial, or "MSN" → partial;
    - anything else → answered.

    *Reason: clicking a clarification chip sets the model and must reach the answered scenario.*
22. **Mock responses get a fresh `MOCK-req-xxxxxxxx` request id per call; their `as_of` stays fixed at 2026-10-31.** *Reason: feedback needs unique ids, and the mock comment-period statuses were computed for that date.*
23. **`/api/eval/latest` serves `data/eval/results.json` if it exists, otherwise the MOCK placeholder.** `/api/feedback` is real and appends to `logs/feedback.jsonl`. *Reason: forward-compatible; there is nothing to mock in feedback.*
24. **The scenario switcher is now a set of dev presets that fill the form and call the real API.** It shows only under `vite dev` with `VITE_SCENARIO_SWITCHER=1` (committed `frontend/.env.development`; no secrets). *Reason: "keep the switcher behind a dev flag", while the response still comes from the backend.*
25. **The Makefile delegates to `scripts/tasks.py`, which runs uvicorn and Vite together** and stops both process trees on exit. *Reason: GNU make isn't on the dev box; `python scripts/tasks.py X` is exactly `make X`.*
26. **Frontend mock data moved to `backend/app/mocks.py`.** `frontend/src/mocks/` now holds only the request presets. *Reason: one copy of the MOCK data, served through the real contract.*

30. **The workbook is read with `dtype=str, keep_default_na=False`.** Raw cells are stored exactly as read (`raw_*`); only empty cells become NULL. *Reason: pandas would otherwise turn text like "NA" or "None" into null.*
31. **REVIEW. A literal two-character backslash-n in 17 summaries is treated as whitespace** in cleaned text; raw is unchanged. *Reason: it's an export artifact that otherwise appears inside sentences.*
32. **REVIEW. PDF artifacts such as "AD 2024- 05-13" and "PC- 6/A-H1" (a space inside an identifier) are NOT repaired.** *Reason: rewriting identifiers is guessing; Prompt 4 extraction must tolerate them.*
33. **The `[ouml]`-style GPO entities in summaries are left as is.** *Reason: they are verbatim source text, and quotes must stay substrings of it.*
34. **Dates are strict `M/D/YYYY` with calendar validation; anything else becomes null and is logged.** Result: 0 unparseable, 4 missing Comments Due Date.
35. **REVIEW. `fr_citation` = "<volume> FR <first page>" only when the Citation contains "Volume N".** 12 rows from 2008–2010 ("Federal Register: July 21, 2010") get null; `citation_text` and `pages` are still stored. *Reason: deriving the volume from the year would be inference.*
36. **Make cells that list several makes (`A | B`, 5 rows) are split.** Each part is canonicalised and stored in `record_makes`; `records.make_canonical` joins them with ` | `. *Reason: a filter on any one listed make must match.*
37. **Canonical display name = the most frequent raw spelling in a normalised-key group** (ties: longer, then alphabetical). *Reason: deterministic, and the name users see most often.*
38. **Explicit merges beyond the key rule:**

    - "Erickson Air-Crane Incorporated DBA Erickson Air-Crane" → "Erickson Air-Crane Incorporated".

    *Reason: the same name plus an abbreviation or DBA suffix.*
39. **REVIEW. Plain "Airbus" (15 rows): none has "Airbus SAS" in its Subject Heading, so all 15 stay "Airbus"** (family Airbus). "Airbus Industrie" (2 rows, 2004 era) also stays separate. Neither was merged into Airbus SAS, per the rule.
40. **REVIEW. Likely same-entity pairs were NOT merged because no rule covers them:** Embraer/Embraer S.A., Cessna/Cessna Aircraft Company, Piper/Piper Aircraft Inc., Gulfstream Aerospace Corporation/LP, the Bell Textron variants, the Pratt & Whitney variants, GE/"GE Aerospace", BAE Systems variants, Eurocopter (the predecessor of Airbus Helicopters). The full list is in docs/make_audit.md. *Reason: the conservative default. Retrieval should use make_family or fuzzy linking so these don't hide records.*

42. **REVIEW. A new docket class `revision_series` (93 groups, 194 rows) was added** beside exact_duplicate / multi_product / correction. Most same-docket groups are NPRM → supplemental/revised NPRM → withdrawal publications, not duplicates. *Reason: the three-class brief misdescribes the data; this lineage drives "latest version" logic in Prompt 4.*
43. **An exact duplicate means the same docket plus identical make_raw, model_raw, subject_heading and summary.** Classes are checked in the order correction, exact_duplicate, multi_product, revision_series.

Result: 5 groups, including real conflicts (Boeing 777 vs Dowty propellers in FAA-2011-0033) and type-certificate transfers (Bombardier → De Havilland).

47. **Splitter rule: a protected abbreviation (U.S., No., Inc., Ltd., Co., S.A., S.p.A., Jr., …) does not end a sentence unless the next word is a strong starter ("This", "The", "We", …).** Periods inside matched brackets never split; unmatched brackets are ignored. *Reason: handles "Bombardier, Inc., Model" and "Textron Inc. This proposed AD" alike. On this dataset the override never fires.*
48. **Ingest regenerates `configs/alias_make.yaml`, `docs/make_audit.md` and `docs/duplicates_audit.md` deterministically on every run**, and builds the DB in a temp file that is atomically swapped in. *Reason: idempotent; rules are reviewed in code, and the yaml is the generated view of them.*

## Prompt 4: rule-based extraction with provenance (items marked REVIEW need a human decision)

49. **`make ingest` = ingest → extract on the temp DB → atomic swap.** A failed extraction never leaves a half-built DB. `python -m backend.app.extract.run` re-runs extraction alone; it drops and recreates its own tables.
50. **Span offsets:** `source=summary` spans are offsets into the Summary; `source=comments` spans are offsets into the Comments text; `source=column` spans are null. *Reason: SPEC only defines Summary offsets, and Comments must stay traceable too.*
51. **REVIEW. `family()` = the part before the first hyphen, but if that part has no digit (DC, BD, EMB, P, MBB) the next segment is included:** DC-9-81 → DC-9, BD-700-2A12 → BD-700, EMB-545 → EMB-545. *Reason: the literal rule makes "DC", "BD" and "P" families, which merges unrelated aircraft.*
52. **REVIEW. Suffix expansion uses the base before the LAST hyphen of the first full designator** ("DC-9-81, -82" → DC-9-82), not the first. It is identical for A330-243 / 777-200. *Reason: the first-hyphen rule gives "DC-82".*
53. **REVIEW. `norm_model` glues letters to numbers only for letter groups of at most 4 characters:** "AS 365 N2" → AS365N2 and "A300 B4-603" → A300B4-603, but "A330-200 Freighter" stays "A330-200 FREIGHTER". "SA-365N" and "SA365N" stay different (hyphens are kept), and "Gulfstream G150" ≠ "G150". *Reason: the literal rule produced "200FREIGHTER". Linking in S1 must handle the remaining variants.*
54. **REVIEW. "737-600, -700, … and 900ER" (a source typo with no dash) gives "900ER" as LOW (`model.summary.orphan_suffix`), not 737-900ER.** *Reason: no guessing; LOW models don't count as an extracted list.*
55. **Model column text without a digit ("radio (also known as radar) altimeter") is LOW `model.column.nondesignator` with model = null.** All-caps hyphenated codes without digits (G-IV, GIV-X, GV-SP) ARE accepted as designators.
56. **Added `model.summary.postfix`:** "PW210A and PW210S model turboshaft engines" and "S-76 model helicopters" (lowercase "model" after the list). *Reason: 8 real extractions the prefix rule cannot see.*
57. **Engine models named in an aircraft record ("767 airplanes equipped with GE Model CF6…") are kept**, with `value.product = "engines"`. *Reason: they are cited in the record; S4 can filter by product.*
58. **REVIEW. `applies_all_of_family` is emitted per family of every model in an "all … Model X" list**, so "all … Model AS350B3" gives family AS350B3. For hyphenless designators the family equals the model, so "all" means all serials of that model. *Reason: the literal "family" wording only makes sense for series lists. S4 must treat it as "all serials of the listed models".*
59. **Serial ranges/lists: NONE exist in the dataset** (0 "X through Y", 0 MSN/S-N numbers). The rules are implemented and tested on SYNTHETIC text only, with REAL negative tests. "certain serial numbers" is not a constraint. *Reason: the brief expected ~19; those summaries only say "certain serial numbers".*
60. **REVIEW. `svcinfo.defined` requires products/serial numbers to be "identified/listed/specified in" service information or a service bulletin; it fires on 0 real records.** "As specified in an EASA AD" (actions) and "unsafe condition identified in the NPRM" are deliberately excluded. *Reason: loose phrases gave only false positives.*
61. **Added rules beyond the brief:**
    - `withdraw.notice`: 123 records are themselves withdrawal notices.
    - `extension.notice`: 4 records announce a comment-period extension.
    - `continue.retain`: "retain the requirements from AD X", MEDIUM.
    - `applicability.add` / `applicability.remove`: MEDIUM.
    - `supersede.unnumbered`: "supersede an existing AD", LOW, no edge.
    - `supersede.negated`: "decided not to supersede", LOW.

    *Reason: needed for status and lineage; all are visible by rule_id.*
62. **AD numbers tolerate PDF spaces ("AD 2024- 05-13" → 2024-05-13) and keep revision suffixes ("72-14-08 R1").** Supersession captures every AD in the clause, including "…; and AD Y, which…".
63. **Lineage edges:**
    - supersedes/continues target "AD n" and are never marked in-dataset (the AD Number column holds each NPRM's final AD number; none is cited).
    - withdraws targets same-docket records issued no later than the notice.
    - comment_extension notices target the other records in their docket.
    - shares_docket edges are written for every same-docket pair.
    - applicability_change targets the record's first superseded/continued AD, else its docket.
64. **REVIEW. R0159's sheet already shows the extended due date (12/09/2024)**, so the extension changes nothing there. `comments_due_effective` logic is proven on a SYNTHETIC row.
65. **New table `record_flags`** (per-record model list + confidence, families, all-families, certain, serial_resolved, svcinfo, is_withdrawal_notice, withdrawn_by). *Reason: precomputed inputs for the S4 engine.*
66. **Coverage denominator = 430 non-duplicate records.** "Model list extracted" counts HIGH or MEDIUM only. `coverage_report.json` uses the CoverageReport API schema; `generated_at` is the source sha1 (not a timestamp), so it stays idempotent.
67. **`docs/extraction_spotcheck.csv` is 25 uniformly random extractions (seed 20261031), written only if the file is absent**, so re-ingesting never overwrites your Y/N labels. Because it is uniform, ~25% are trivial Model-column rows. Precision: `python scripts/spotcheck_precision.py` (with a Wilson 95% interval).
68. **Ruff E501 is ignored in `backend/tests/*`.** *Reason: golden tests embed verbatim real sentences.*

## Prompt 5: applicability and revision engine (items marked REVIEW need a human decision)

69. **The CLI is `python -m backend.app.engine.explain` (package `backend.app`), not `app.engine.explain`.** `--bench` times the engine over all records.
70. **REVIEW. Two match outcomes added to SPEC's four:**
    - `SERIES_OVERLAP`: the record lists a series ("A330-200", "737-900 series") and the query is a variant that may belong to it (A330-243, 737-900ER).
    - `SPELLING_VARIANT`: the same designator up to punctuation or a leading name (SA-365N/SA365N, GULFSTREAM G150/G150).

    Both give UNDETERMINED, never NOT_APPLICABLE, and neither can produce APPLICABLE, so this is not fuzzy matching. *Reason: without them, 8 real A330-200-series records would wrongly say NOT_APPLICABLE for an A330-243.*
71. **REVIEW. `applies_all_of_family` counts as EXACT only when the whole-type designator itself is listed** ("all … Model A318 series" → A318). *Reason: R0061 says "all Airbus SAS Model A330-243, A330-243F, …"; the literal rule would make it APPLICABLE to an A330-202 it never lists. The guard is enforced in both the loader and `match_model`.*
72. **A record that lists the whole type ("Model A330 and A340 airplanes") matches any variant of it (EXACT, "family_level").** *Reason: over-inclusion is the safe direction.*
73. **REVIEW. NO_MATCH is UNDETERMINED (not NOT_APPLICABLE) whenever the record has LOW-confidence model tokens** (an orphan "900ER" or a non-designator). *Reason: the list may be incomplete. This applies the safety invariant to "MEDIUM list + LOW leftovers".*
74. **REVIEW. Related makes:** when the normalised keys share a first word (Embraer / Embraer S.A., Bell variants), the make check does not exclude; the model check decides. A make-family match (Airbus SAS vs Airbus Helicopters) also passes the make check, per the spec.
75. **Make given but no model → UNDETERMINED ("model applicability was not checked").** *Reason: SPEC defines NOT_CHECKED only for no make and no model; APPLICABLE would overclaim.*
76. **Serial supplied + `qualifier_certain`, with no service-info wording, uses its own reason** ("affects only certain airplanes … summary does not say which serial numbers"). The verdict is UNDETERMINED as specified; the service-information wording is reserved for `svcinfo`.
77. **An exclusion wins over an inclusion range** (a serial inside a range but in an "except" list → NOT_APPLICABLE). Different prefixes or formats → UNDETERMINED (`serial.incomparable`).
78. **Evidence ids:** sentence ids for Summary evidence; `R0001#col:Model` / `#col:Subject Heading` / `#col:Comments` for column-based evidence. Every NOT_APPLICABLE carries `basis` (the confidences it rests on); a test asserts it is always HIGH/MEDIUM.
79. **Withdrawn = any record whose `withdraws_docket` equals this record's docket (docket-level, as specified).** The withdrawal notice itself is therefore also "withdrawn"; the UI should label it as the notice.
80. **REVIEW. New extraction rule `withdraw.subject` (HIGH, source=column): Subject Heading contains "Withdrawal"**, used only when the Summary shows no withdrawal. *Reason: R0294 (an empty Summary) is the withdrawal notice for docket 2000-NM-120-AD; without it, 4 records showed as not withdrawn.*
81. **`is_latest_in_docket_group`:** the latest `citation_publish_date` among non-duplicates; ties mark all tied records as latest; duplicates are never latest.
82. **`superseded_by_proposal` uses only the AD Number column.** In the real data it is empty for every record (no NPRM's final AD number is cited elsewhere), and a test asserts this so the claim stays honest.

## Prompt 6: hybrid retrieval (items marked REVIEW need a human decision)

83. **The CLI is `python -m backend.app.retrieval.search` (package `backend.app`).** `--bench N` prints p50/p95 per mode; `--compare` shows the three rankings side by side.
84. **Embedding backend: BAAI/bge-small-en-v1.5 (384-d) loaded from the local Hugging Face cache.** It was installed with CPU-only torch 2.15 and sentence-transformers 6.2 on Python 3.14. The TF-IDF char 3–5-gram fallback is logged as a WARNING and named in `/api/meta` with the reason. `ADTRACE_EMBEDDINGS=tfidf` forces it (used by tests for speed).
85. **The sanitiser keeps only `[A-Za-z0-9]` tokens (with internal - or /), double-quotes each, ORs them, and drops stopwords including AND/OR/NOT/NEAR.** Tokens with a digit also get a prefix match (`"a330"*`) and their norm_model() form. *Reason: with "-" as a token character, a bare "A330" would otherwise never match "A330-243"; OR (not AND) suits natural-language questions.*
86. **REVIEW. Hard filters mirror the engine instead of plain equality:**
    - the make filter removes only records the engine calls a "different" manufacturer, so make-family and related spellings stay, and records with no make stay;
    - the model filter removes only HIGH/MEDIUM, complete lists that NO_MATCH, so series overlaps, spelling variants and unknown lists stay;
    - the date filter keeps undated records.

    *Reason: retrieval must never hide a record the engine would keep as UNDETERMINED. The cost is that a make filter for "Airbus SAS" keeps 85 Airbus-family records.*
87. **REVIEW. `extra_sentence_bonus` is 0.02, not 0.1.** RRF steps are about 0.0003 per rank, so 0.1 let a record with three mediocre sentences (R0012, radio altimeter) outrank the record ranked #1 by both BM25 and dense (R0003, radio management panel). To be tuned on the dev split (Prompt 11).
88. **Records with an empty Summary (R0294) have no sentences, so they are reachable only through `records_fts`, as a `<rid>#heading` unit (BM25 only).** The evidence is the Subject Heading with no span. *Reason: otherwise they could never be retrieved, and EMPTY_SOURCE_TEXT could never be raised.*
89. **The single-ranker modes (`bm25`, `dense`) use the same 1/(k+rank) scoring and aggregation as hybrid**, so the three baselines differ only in which rankings are fused.
90. **`top_bm25_norm` = s/(1+s), where s = −bm25()** (saturating 0..1). No thresholds are set here (Prompt 11).
91. **The dense cache is `data/index/emb_sentences.npy`, `ids.json` and `emb_meta.json`.** The version hash covers the model name and every header-prefixed text. `make ingest` re-embeds only on a hash change (about 20 s on this laptop).
92. **The app warms the Retriever in a FastAPI lifespan hook (about 5 s).** `ADTRACE_SKIP_WARM=1` skips it. Failures are reported in `/api/meta.embedding_backend`, never swallowed. Set `HF_HUB_OFFLINE=1` to avoid Hugging Face HEAD requests at startup once the model is cached.
93. **The cross-encoder rerank is implemented behind `retrieval.rerank.enabled` (default false) and untested.** *Reason: the spec says optional and off by default; it adds a second model download.*

## Prompt 7: query understanding, entity linking, gates (items marked REVIEW need a human decision)

94. **REVIEW. No `temperature` is sent.** Claude Haiku 5.5 and Claude Sonnet 5.5 reject non-default sampling parameters with a 400, and API version 2026-10-21 rejects them on every model. Determinism (H11) comes from the sha256-keyed response cache, pinned model IDs and fixed prompts. `models.temperature` was removed from config.yaml.
95. **REVIEW. Forced tool use only where the model allows it.** Claude Haiku 5.5 (the parser and verifier) gets `tool_choice: {type: "tool"}` with thinking disabled and effort low. Claude Sonnet 5.5 (the generator) returns a 400 on forced `tool_choice`, so it gets `tool_choice: auto` + `strict: true` + an explicit instruction, and a missing tool call counts as invalid output (retried once, then LLMError). Per-model options are in `config.yaml` `llm.model_options`.
96. **Model IDs verified against Anthropic's current model list (cached 2026-10-06): `claude-sonnet-5-5` and `claude-haiku-5-5` are current.** Pricing in config: Haiku $0.10/$0.50, Sonnet $2/$10 per MTok (first-party list prices; the logged cost is an estimate).
97. **Tool schemas are sent with `strict: true`.** `strict_schema()` inlines $refs and closes every object (`additionalProperties: false`, all properties required); nullable fields stay `anyOf [T, null]`.
98. **Credentials:** the client loads `./.env` then `./data/.env` (existing env vars win) and refuses locally, without sending, any `ANTHROPIC_API_KEY` that does not start with `sk-ant-` or contains whitespace. The key is never logged; a test checks the call log and cache files.
99. **REVIEW. Make linking deviates in two places from "token_set_ratio ≥ 90 accept":**
    - an exact name/alias match wins outright;
    - several makes ≥ 90 → AMBIGUOUS_MAKE ("Bell", "Gulfstream", "Rolls Royce");
    - when the query has more words than a candidate name, the score is capped at `token_sort_ratio`, so "Lockheed Martin Skunk" no longer auto-accepts "Lockheed".

    Cost: "boeing co" now asks for clarification (score 80).
100. **REVIEW. A bare family with 2+ variants is AMBIGUOUS_MODEL even if the family string is itself a vocabulary entry** ("A330", "737", "A318"). An exact designator with at most one variant is accepted ("PW4090" vs "PW4090-3"). Options are capped at 12 and narrowed to the linked make's variants when that leaves any.
101. **The empty query with no make/model uses NO_RETRIEVAL_HIT** (no dedicated code in SPEC); an empty query with UI make + model passes (lookup by configuration).
102. **REVIEW. Out-of-scope keywords are skipped when the question asks what the proposal itself says** ("What does the proposal say about torque…" is in scope; R0001's summary mentions torque).
103. **False premises:**
     - "AD in the dataset" means it is mentioned in any sentence, cited by a supersedes/continues extraction, or in the AD Number column.
     - The engine check runs only on records that *describe* the AD's applicability (supersede/continue or AD Number column).
     - CONTRADICTS_RECORD only if every such record is NOT_APPLICABLE for the premise's make/model.
     - Premises whose make/model can't be linked are left "unchecked", never refused.
104. **Gate order: empty → injection → out of scope → entities → premises.** NO_RETRIEVAL_HIT and EMPTY_SOURCE_TEXT run after retrieval. LOW_RETRIEVAL_SCORE and APPLICABILITY_UNDETERMINED are explicit hooks that never stop yet (Prompt 10).
105. **The FAKE LLM (`LLM_MODE=fake`) has a crude regex fallback for `parse_query`**, so the CLI works offline; tests always register their own outputs. The live test is marked `live` and deselected by default (`pytest -m live`).

## Prompt 8: grounded generation (items marked REVIEW need a human decision)

106. **REVIEW. Sonnet 5.5 generation runs with `thinking: between_tools` (its lowest setting), effort medium, `max_tokens` 1200, and no temperature.** Thinking counts toward `max_tokens`, so adaptive thinking could exhaust the 1200-token budget before the tool call. A `max_tokens` stop is an LLMError, which falls back to the extractive answer.
107. **Validation in two layers:**
     - Pydantic (schema; ≤ 5 rationale steps) plus `pack_violations` (hard rules: ≤ 6 claims; every evidence/fact id must exist; each claim needs evidence_ids + quote, or fact_ids; a quote needs an evidence id; 2–5 rationale steps unless cannot_answer) trigger the single retry, then LLM_ERROR → extractive fallback.
     - Word-count and "ends with [ids]" limits are soft `style_warnings`: Prompt 9 verification decides what survives.

     The strict tool schema drops `maxItems`/`maxLength` (not supported in strict mode); Pydantic enforces them.
108. **Pack:**
     - At most 14 sentences, chosen round-robin across the top records in retrieval order. Within a record, engine anchor sentences come first, then relevance; the output is ordered by record then sentence index.
     - `fr_citation` = the parsed "91 FR 66016" form (falls back to the raw Citation text).
     - Multi-make records show at most 3 makes + "(+N more)".
     - Dataset and user text are HTML-escaped (`&`, `<`, `>`; attributes also `"`). Prompt 9's quote check must unescape before comparing.
     - The exact pack text is returned in `GenerationResult.pack.text`; Prompt 10 writes it to the audit log.
109. **Computed facts are generated from the engine's Applicability, RecordStatus and Lineage.** Applicability lines carry the evidence ids; lineage lines carry extraction ids. "would supersede AD X (target not in dataset)" is always worded as a proposal.
110. **The extractive answer uses each of the top 3 records' most relevant sentence verbatim (quote = full sentence), plus every computed fact for that record as its own claim.** It has no rationale steps and may exceed 6 claims. `mode` is `extractive` (search_only) or `extractive_fallback` (LLM error, with the error text). The UI shows a banner from the S6 trace detail `answer_mode`.
111. **REVIEW. Retrieval fix 1 (found while building packs): within-record evidence is now ranked by RRF of a sentence-text-only BM25 (record columns weighted 0) and cosine.** Every FTS row repeats the record's models, so a model in the query lifted all of a record's sentences equally, and length normalisation picked the shortest ("This proposed AD also reduces the applicability.") over the radio-management-panel sentence R0003#s2.
112. **REVIEW. Retrieval fix 2: with a make/model filter, the final record order is tiered by the engine match before score.**
     - Tier 0 = the record lists the aircraft (EXACT / whole type / all-family).
     - Tier 1 = possible (series overlap, spelling variant, family-only).
     - Tier 2 = no model list or no make.

     Without it, ~50 records with no model list (kept so UNDETERMINED is visible) outranked R0002, which lists PW4090. `features.tier0_records` reports how many records matched outright.
113. **`engine.explain.link_model` (used by the CLIs) now uses the same family rule as `pipeline.linker`** (an exact designator with ≤ 1 variant is a model): PW4090 had been treated as a family.
114. **`scripts/live_generate.py` runs the 3 live queries** (pack, raw tool output, tokens/cost). It is blocked until `data/.env` holds a real key; until then each query shows the extractive fallback with the reason.

## Prompt 9: verification layer (items marked REVIEW need a human decision)

115. **Layers are switched by `config.yaml` `verify.{quotes,grounding,llm}` and per call by `verify(..., layers={...})`** (ablation). With `quotes` off, a quote is still located for highlighting but never drops a claim.
116. **Quote normalisation:**
     - Steps: HTML-unescape (the pack is escaped), NFKC, curly→straight quotes, all dash characters → "-", casefold, whitespace collapsed, surrounding punctuation stripped from the quote.
     - Matching is done on a character index map, so spans point at exact Summary offsets.
     - A quote must lie inside ONE cited sentence.
     - Extra reason code `QUOTE_MISSING`: evidence is cited but there is no quote.
117. **REVIEW. AD numbers and ISO dates share the shape YYYY-NN-NN, so they are compared as one "code" set.** Dates written as "December 3, 2026", "3 December 2026" or "12/3/2026" are converted to ISO first. A claim's AD number therefore also counts as grounded if the same string is a cited date (accepted risk; it has not happened in the fixtures).
118. **Grounding haystack = cited sentences + cited fact lines + cited ids + cited records' docket, AD Number, FR citation, pages, make and FULL model list.** The pack's `<e>` attribute shows at most 10 models, but PackRecord keeps all of them for grounding. Numbers are grounded if they appear anywhere as a digit run in the haystack, so this is permissive for numbers that are part of designators.
119. **REVIEW. Mandate check:**
     - Drops any claim containing requires / required / must / mandatory / mandates / shall / effective immediately without propose* / would / notice / NPRM.
     - Exception: "AD <number> requires…" describes an existing final AD cited by the proposal (R0003#s2 does this), and the AD number must itself be grounded.
     - Known false-positive risk: "The existing AD requires…" (no number) is dropped.
120. **REVIEW. Fact consistency is checked only against cited *applicability* facts:**
     - The claim's stance (negative phrases first) comes from the keyword table in `configs/rules.yaml`.
     - Conflicts: APPLICABLE wording vs a NOT_APPLICABLE / UNDETERMINED / NOT_CHECKED fact; NOT_APPLICABLE wording vs APPLICABLE / UNDETERMINED / NOT_CHECKED; UNDETERMINED wording vs NOT_APPLICABLE.
     - A cautious downgrade ("may apply" when APPLICABLE with "certain airplanes") is allowed.
     - Status facts ("comment period closed") are left to the LLM layer.
121. **Verifier input per item: the claim, plus its quote and/or the cited fact lines (prefixed with record id).** No question and no other evidence; a test asserts this. Claims whose text equals their quote are SUPPORTED without a call ("verbatim"). Extractive answers skip the LLM layer: there is no model wording to audit.
122. **REVIEW. If the verifier call fails (LLMError), every claim that needed it is dropped with VERIFIER_ERROR** (fail closed). The status becomes VERIFICATION_FAILED, or partial if verbatim/extractive claims survived. Prompt 10 should then show the extractive answer.
123. **Rationale steps need ≥ 1 existing evidence/fact id in brackets and must pass entity grounding against the ids they cite** (no mandate/fact checks). Fewer than 2 surviving → `rationale_steps` is empty, and the UI hides the panel.
124. **Status:**
     - all kept → answered;
     - some kept → partial ("N statements removed because they could not be verified.");
     - none kept → refused with VERIFICATION_FAILED;
     - model cannot_answer → refused with no code (Prompt 10 maps it).

     `to_api_claims()` emits only kept claims with `verification="verified"`. A fact citation uses `evidence_id = "<record>#F<n>"`, so the drawer opens the record.
